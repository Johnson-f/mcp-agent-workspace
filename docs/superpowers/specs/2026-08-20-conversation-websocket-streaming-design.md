# Conversation WebSocket Streaming Design

## Objective

Stream conversational model responses into the UI in real time and replace the static Conversation header with an AI-generated title based on the first meaningful user message.

The WebSocket transport changes delivery, not product authority. A model-generated Automation Proposal remains inert until the user reviews it, explicitly configures tools and permissions, and approves the Automation.

## Connection

The browser connects to the Fastify API at:

```text
/ws/conversations/:conversationId
```

The public WebSocket origin is configured through `NEXT_PUBLIC_BACKEND_WS_URL`. Local development defaults to `ws://localhost:6020`.

The browser automatically sends normal cookies during the WebSocket upgrade. The API authenticates the Stytch session and confirms that the user belongs to the Conversation's Workspace before accepting messages.

Local development authentication may use the configured development user only while `AUTH_DEV_BYPASS=true` and `NODE_ENV` is not `production`. Production WebSocket connections never accept a development identity.

## Wire Protocol

Every frame is a JSON object with a versioned `type` discriminator.

### Client To Server

```ts
type ConversationClientMessage = {
  type: "user_message";
  clientMessageId: string;
  content: string;
  mode: "chat" | "automation";
};
```

`clientMessageId` is generated by the browser and provides idempotency for reconnects or accidental duplicate sends.
`chat` preserves natural conversation and may still detect clear automation intent. `automation` guarantees a reviewable proposal for that message, but never bypasses configuration or approval.

### Server To Client

```ts
type ConversationServerMessage =
  | {
      type: "connection_ready";
      conversationId: string;
    }
  | {
      type: "turn_started";
      clientMessageId: string;
      turnId: string;
    }
  | {
      type: "user_message_accepted";
      clientMessageId: string;
      messageId: string;
    }
  | {
      type: "conversation_title";
      title: string;
    }
  | {
      type: "assistant_delta";
      turnId: string;
      delta: string;
    }
  | {
      type: "automation_proposal";
      turnId: string;
      proposal: AutomationProposal;
    }
  | {
      type: "turn_completed";
      turnId: string;
      messageId: string;
    }
  | {
      type: "turn_failed";
      turnId: string | null;
      code: string;
      message: string;
      retryable: boolean;
    };
```

The protocol never streams raw model reasoning, raw provider events, credentials, or raw MCP results. A later display-safe contract may stream provider-generated reasoning summaries as normalized Conversation activities.

## Turn Lifecycle

1. Validate the frame and reject blank or oversized content.
2. Verify Conversation ownership again before starting the turn.
3. Reject a second user message while the Conversation already has an active turn.
4. Persist the user message using `clientMessageId` as an idempotency key.
5. Emit `user_message_accepted` and `turn_started`.
6. Start title generation in parallel when the Conversation still has its default title.
7. Send bounded append-only Conversation history and the `propose_automation` tool to the model.
8. Emit each model text fragment as `assistant_delta`.
9. Emit `automation_proposal` if the model calls `propose_automation`.
10. Persist the completed assistant message and proposal metadata.
11. Emit `turn_completed`.

Only one model turn may run per Conversation. Other Conversations may stream concurrently.

## Model Streaming

The model provider exposes a callback or async-iterator interface that emits normalized events:

```ts
type ConversationModelStreamEvent =
  | { type: "text_delta"; delta: string }
  | { type: "automation_proposal"; proposal: AutomationProposal };
```

Provider-specific Responses API SSE events remain private to the model adapter. Both API-key and Codex-subscription authentication use the same normalized stream interface. Deterministic fallback mode emits one complete text delta.

The existing non-streaming execution path remains available for durable Automation Run activities.

## Conversation Titles

The title is generated in parallel with the first assistant response.

Requirements:

- Describe the subject or intended work, not the user's wording style.
- Use plain sentence case.
- Contain between 3 and 80 characters.
- Exclude quotation marks, trailing punctuation, markdown, and labels such as “Title:”.
- Never contain secrets or hidden model reasoning.

If title generation fails, use a whitespace-normalized, bounded version of the first user message. Persist the title before emitting `conversation_title`.

The App header, Conversation page title, and sidebar row all use the persisted Conversation title. The browser updates all three immediately after receiving `conversation_title`.

## Persistence

Conversation messages remain append-only.

Add message metadata for:

- `clientMessageId` on user messages.
- `turnId` on assistant messages.
- `automationProposal` when present.
- `incomplete: true` when a disconnected or failed turn produced partial visible text.

Add a unique partial index for non-null user `clientMessageId` values within a Conversation. Duplicate client messages return the previously persisted user message and do not start another model turn.

Completed assistant messages are persisted once. If generation fails after text has been emitted, persist the partial assistant text with `incomplete: true`, then emit `turn_failed`.

## Cancellation And Disconnects

Every active turn owns an `AbortController`.

- Closing the WebSocket aborts the model request for that socket's active turn.
- The server persists non-empty partial assistant text as incomplete.
- No `turn_completed` event is emitted after cancellation.
- A fresh connection reloads persisted history through the existing Conversation detail RPC.

The first version does not replay missed deltas. Persisted messages are the reconnect authority.

## UI Behavior

When sending:

- Enter sends.
- Shift+Enter inserts a newline.
- The user message appears optimistically with `clientMessageId`.
- A live assistant bubble appears after `turn_started`.
- `assistant_delta` appends text without recreating the component.
- A subtle active indicator is shown while streaming.
- The composer is disabled only for the active Conversation turn.
- Stop generation closes the active turn through a `cancel_turn` client frame in a follow-up version; the initial version aborts on disconnect.

On completion, the UI reconciles with persisted Conversation detail. On failure, partial output remains visible with an incomplete marker and a retry action.

## Header And Sidebar

The route-aware App header resolves Conversation IDs and loads the persisted title. Static copy such as “Conversation — Chat with the AI…” is removed for Conversation routes.

The sidebar continues to use pinned/recent history. A `conversation_title` event updates the matching row immediately, and a subsequent history refresh confirms server state.

## Error Handling

- Invalid JSON: send `turn_failed` with `invalid_frame` and keep the socket open.
- Unauthenticated upgrade: reject with HTTP 401.
- Unauthorized Conversation: reject with HTTP 404 to avoid disclosing existence.
- Active turn conflict: send `turn_failed` with `turn_in_progress`.
- Provider failure before text: emit retryable `turn_failed` without an assistant message.
- Provider failure after text: persist incomplete assistant output and emit retryable `turn_failed`.
- Persistence failure: abort generation and emit non-retryable `turn_failed`.

User-visible errors never expose provider response bodies, credentials, tokens, database errors, or stack traces.

## Security And Limits

- Maximum incoming message: 32 KB UTF-8.
- Maximum history messages sent to the model: 40.
- Maximum content per historical message: 10,000 characters.
- Maximum streamed assistant text: 64 KB.
- WebSocket origin must match an allowlisted application origin.
- Use secure `wss://` outside local development.
- Automation Proposals grant no permissions and trigger no tools.

## Acceptance Criteria

- “hey” streams a normal assistant response without an Automation Proposal.
- A recurring-work request streams text and an inert Automation Proposal.
- Text becomes visible before the model turn finishes.
- The first meaningful message produces a persisted title no longer than 80 characters.
- The header and sidebar update to the generated title without a page reload.
- Reopening the Conversation shows persisted messages and title.
- Duplicate `clientMessageId` frames do not duplicate messages or model calls.
- Disconnecting aborts generation and persists non-empty partial output as incomplete.
- One Conversation cannot run two simultaneous model turns.
- No Automation becomes live without the existing explicit approval gates.
